Extended Abstract: A Unified Dual-Transport Python Framework for Pre- and Post-Silicon RISC-V Debug Compliance

Abstract

The RISC-V Debug Specification defines a complex, highly-stateful interaction protocol between an external debugger and the on-chip Debug Module (DM). Verifying this compliance traditionally suffers from a sharp disconnect: pre-silicon teams rely on SystemVerilog/UVM testbenches generating stimulus via the Debug Module Interface (DMI), while post-silicon teams use software debuggers communicating over physical JTAG. This fragmentation results in duplicated effort, untraceable bugs, and delayed silicon bring-up. We propose a unified, dual-transport Python orchestration framework that resolves this dichotomy. By abstracting the transport layer and utilizing a deeply decoupled, testbench-agnostic UVM bridge, the framework allows the exact same Python debug compliance scenarios to execute seamlessly against both a UVM simulation and physical silicon. This enables true "shift-left" verification for debug infrastructure, ensuring that post-silicon validation tests are thoroughly proven in RTL simulation long before tape-out.

1. Introduction

Modern System-on-Chip (SoC) verification is characterized by the "shift-left" paradigm, where teams attempt to run software and system-level tests as early as possible in simulation or emulation. However, hardware debug infrastructure—specifically the RISC-V Debug Module—often resists this paradigm due to the inherent divide in how pre-silicon and post-silicon teams operate.

Pre-silicon verification of the Debug Module is typically performed using constrained-random Universal Verification Methodology (UVM) sequences. These sequences are excellent for verifying DMI bus protocol compliance and corner-case timing, but they are generally poor at capturing the high-level, stateful workflows of a real debugger. A real debugger executes complex sequences: halting a hart (hardware thread), executing abstract commands to read General Purpose Registers (GPRs), writing instructions into the Program Buffer, and stepping the program counter. Writing these state-dependent, highly sequential workflows purely in SystemVerilog is cumbersome and heavily ties the tests to the specific verification environment.

Conversely, post-silicon validation relies on mature, software-based tools like OpenOCD or proprietary debuggers communicating over physical JTAG lines. When a post-silicon debug test fails on the lab bench, root-causing the failure is exceedingly difficult because the hardware stimulus (the exact sequence of JTAG shifts) cannot be natively or easily replayed in the UVM simulation environment. Verification engineers are often forced to manually translate software debug logs into SystemVerilog sequences to reproduce bugs in RTL, a process that is error-prone and highly time-consuming.

To bridge this gap, verification engineers need a unified mechanism to define debug workflows once, and execute them across any target. The framework presented in this paper solves this by decoupling the intent of a debug test (which registers to read or write, and the logical assertions to make) from the transport (the physical or simulated medium used to communicate with the chip), enabling a single Python-based test suite to drive both UVM simulations and physical hardware identically.

2. Background: The RISC-V Debug Specification

To understand the necessity of this framework, one must understand the architecture of the RISC-V Debug Specification. The specification defines a standard Debug Module (DM) that acts as the interface between an external debugger and the internal RISC-V harts.

Communication with the DM occurs over the Debug Module Interface (DMI), a simple address/data bus protocol. The DM contains a register map (e.g., dmcontrol, dmstatus, abstractcs, data0). When an external debugger wishes to read a register from the CPU, it does not do so directly. Instead, it writes a command to the abstractcs (Abstract Command and Status) register in the DM. The DM hardware then stalls the CPU, extracts the requested register value, places it into the data0 register, and sets a status flag. The external debugger must poll this status flag, and upon success, read the data0 register.

This highly stateful, hand-shaking protocol means that testing debug compliance is not about firing random bus transactions; it is about executing precise sequences of reads and writes, making decisions based on the read data, and handling hardware state transitions. Python, as a high-level scripting language, is exceptionally well-suited for modeling these state machines, whereas SystemVerilog is not.

3. Architectural Vision: A Dual-Transport Paradigm

The core of our solution is a strictly layered architecture driven by external configuration files. The system is entirely decoupled, ensuring that the high-level orchestration logic remains wholly ignorant of whether it is communicating with a cycle-accurate RTL simulation or a physical ASIC.

The workflow begins with a JSON configuration file. This file dictates the scenario to execute, the target transport layer to initialize ("uvm" for simulation, or "openocd" for hardware), and any scenario-specific parameters such as base memory addresses for scanning. A master Python runner parses this configuration, dynamically loads the requested scenario script, initializes the transport, and executes the sequence. This approach allows continuous integration (CI) systems to run the exact same regression suite against nightly RTL builds and against physical FPGA prototypes simply by swapping the JSON configuration file.

4. The Python Orchestration Layer

At the highest level, test scenarios are written using a fluent, object-oriented Python API that models the RISC-V Debug Module. A scenario is constructed as a DebugSession consisting of discrete, ordered steps.

For example, a typical "halt" scenario involves: 1. Activating the module by writing to dmcontrol. 2. Requesting a halt by setting the haltreq bit. 3. Polling the dmstatus register until the allhalted bit is asserted. 4. Issuing an abstract command to read the Program Counter (PC).

Crucially, this Python API does not implement JTAG state machines or DMI bus cycles. It simply yields abstract, high-level register access requests: write(addr=0x10, data=0x80000001) and read(addr=0x11). The underlying transport class intercepts these abstract requests and serializes them according to the target execution environment. This strict separation of concerns ensures that the test scenarios are universally reusable, eliminating the need to maintain separate test suites for different phases of the silicon lifecycle.

5. Pre-Silicon Flow: The Testbench-Agnostic UVM Bridge

The most significant technical hurdle in co-simulation is integrating an external, asynchronous Python process with a synchronous, cycle-driven UVM environment without heavily modifying the legacy testbench. Many existing co-simulation solutions rely on complex Direct Programming Interface (DPI-C) call chains that tightly couple the C code to specific UVM components. This makes the solution fragile, difficult to debug, and nearly impossible to port to other projects.

Our framework introduces a deeply decoupled, testbench-agnostic bridge utilizing a thread-safe pull architecture.

  1. Thread-Safe C Socket Server: At simulation time-zero, the UVM test calls a DPI function to spawn a POSIX thread running a Unix domain socket server. This background thread listens for JSON-formatted commands from Python.
  2. Pull-Based DPI Polling: Instead of the C thread attempting to asynchronously call into SystemVerilog (a process that requires complex scope management and is inherently unsafe in many commercial simulators), the UVM environment pulls requests from the C thread. A dedicated python_bridge UVM component continuously polls a C function (dpi_bridge_get_req()). The C thread utilizes mutexes and condition variables to safely hand off data across the thread boundary to the simulator's main execution thread.
  3. Native Sequence Generation: When the UVM bridge receives a read or write request, it dynamically instantiates a native SystemVerilog sequence (e.g., dmi_write_seq) and starts it on the testbench's existing UVM sequencer.
  4. Complete Decoupling: Because the bridge communicates with the rest of the testbench purely through standard UVM sequence items, the existing UVM Agent, Driver, Monitor, and Scoreboard remain completely unmodified and entirely unaware of the Python orchestrator. Integrating this framework into a third-party testbench requires instantiating a single UVM component and passing it a pointer to a sequencer.

Furthermore, the protocol includes a graceful shutdown opcode. When the Python scenario completes successfully or encounters a fatal error, it sends a shutdown command, prompting the UVM bridge to safely drop its UVM objection, allowing the simulation to end cleanly and report coverage without relying on arbitrary watchdog timeouts.

6. Post-Silicon Flow: Bypassing High-Level OpenOCD Constructs

When the JSON configuration targets real hardware (an FPGA prototype or physical ASIC), the framework swaps the UVM transport for the OpenOCD transport. OpenOCD is an industry-standard open-source tool that interfaces with physical USB debug probes and drives the JTAG protocol.

OpenOCD provides a standard TCL command server on TCP port 6666, allowing external programs to connect via standard network sockets and send text-based commands. While OpenOCD features built-in, high-level commands for RISC-V debugging (such as halt, resume, or reg), our framework deliberately bypasses them.

If we utilized OpenOCD's high-level halt command, OpenOCD would internally generate the sequence of DMI register writes required to stop the core. In doing so, we would be verifying OpenOCD's internal state machine logic rather than our hardware's specification compliance. Instead, we must ensure that the physical chip receives the exact same sequence of individual register accesses that the UVM simulation received.

When the Python scenario requests a register write, the OpenOCD transport driver translates this directly into a low-level TCL string, such as riscv dmi_write 0x10 0x80000001.

In this flow, OpenOCD acts purely as a dumb protocol translator: 1. It receives the DMI write command via TCP. 2. It constructs the appropriate JTAG Instruction Register (IR) scan to select the DMI scan chain within the physical chip. 3. It constructs the Data Register (DR) scan containing the exact address, data, and operation bits requested by Python. 4. It translates these logical scans into physical USB commands for the debug probe (such as an FTDI-based J-Link or Olimex), which generates the electrical signals (TCK, TMS, TDI) on the physical pins.

By restricting OpenOCD to a low-level protocol translation role, the framework guarantees that the sequence of register operations executed on physical silicon is bit-for-bit identical to the sequence simulated in UVM. This ensures true apples-to-apples validation.

7. Results and Conclusion

The implementation of this unified, dual-transport Python framework fundamentally alters the debug verification lifecycle, eliminating silos between pre-silicon and post-silicon teams.

  1. Zero-Overhead Portability: Verification engineers can develop, debug, and rapidly iterate on complex, highly stateful debug scenarios using RTL simulation, leveraging full waveform visibility. Once the simulation passes, those exact same Python scripts are executed against first silicon on day one in the post-silicon lab, without rewriting a single line of code.
  2. Deterministic Debugging: If a test scenario fails on physical hardware but passes in RTL simulation, engineers can definitively rule out logical errors in the test sequence. The discrepancy is instantly isolated to physical design, synthesis, clock-domain crossing issues, or analog pin integrity, because the logical stimulus delivered to the Debug Module is mathematically proven to be identical.
  3. Seamless Integration: The use of a deeply decoupled, sequence-driven UVM bridge ensures that legacy SystemVerilog testbenches can adopt Python-driven orchestration with near-zero refactoring overhead.

By bridging the gap between SystemVerilog testbenches and physical hardware debuggers, this framework dramatically reduces test development time, eliminates duplicated effort, and drastically accelerates the silicon bring-up and compliance validation process for RISC-V cores.
